DayPage · Architecture Design Review

暂存区、Skills、存储与 Feed

把捕获与编译解耦,让手机只做轻量记录,让 AI 能力以可插拔的 skill 形式生长——这份文档整合我们几轮讨论的结论,供评审。

历史设计探索。这不是当前架构或实现计划。示例均已匿名化，仅用于评审；当前要求以 docs/README.md、GitHub issue、已接受 ADR、代码与测试为准。

00 · 核心原则

它只做暂存,不做第二大脑

「暂存 vs 第二大脑」不是一次产品分叉,而是「用户开了哪些 transform skill」的一个配置。

暂存区在中间:多入口零阻塞地把碎片写进来,不 block AI。想要清爽的人,把编译/抽取全部关掉,它就是一个极快的 fleeting inbox;想要沉淀的人,把 transform 管道打开,它才「长成」第二大脑。这样一来,你上次苦恼的「编译 wiki 管理成本高」被彻底化解——没被 promote 的条目自然衰减进 archive,你永远不必去 curate。

01 · 分层架构

A.暂存区居中,skills 是接管子

整套地基是「文件 = 契约 = API」。三类管道分别负责「进来」「内部转化」「出去」,数据库作为可重建的旁路索引挂在契约层下面。

02 · 三类 Skill 家族

B.AI 能力的三种形状

不要把日/周/月编译写成几个并列的 Swift service。它们是同一种 skill 的参数化——用声明式 recipe 表达差异。

编译类 · Compile

时间窗 → 叙事 wiki

日 / 周 / 月 / 年。差异只有四个:输入层级 · 时间窗 · prompt 模板 · 落盘路径(+ dedup key)。raw→daily→weekly 是金字塔 rollup,上层编译下层,而非每层重扫 raw。抽象成 recipe manifest。

抽取/富化类 · Extract

内容 → 类型化卡片

现有 entity、mood,未来 book / expense / place / workout……这才是「针对卡片灵活扩展的 skills」。加一种卡片 = 加一个抽取 skill,不动主干。

派发/发布类 · Dispatch

暂存 → 外部世界

生成器(daily-todo)与 sink(dispatch-ticktick / -reminders)拆开:一个生成器、多个收件端,用户在配置里选。每个 task 带稳定 source id → 重跑是 update 不是重复。

输入 = 捕获 + 命令,靠一个意图路由统一:默认永远是捕获(拿不准就存);只有明确到不会误判的输入才路由到命令(编译 / 派发 / 发布)或问答。对外部 app 的写操作,首次必须二次确认——微信自由文本场景尤其重要。

03 · 存储决策

C.文件是真相,数据库是可重建索引

元信息的访问模式和正文完全不同,但不能动「文件=契约」的地基。答案是分清主从的混合方案。

DECISION 文件 = Source of Truth · SQLite = 派生索引 · 只有文件同步

杀手级好处在你的多端/游牧场景:只有文件同步,数据库永不同步。 每台设备从同步下来的 vault 各自重建自己的 SQLite。于是永远没有数据库合并冲突,只需要 merge Markdown——而 Markdown 天生 diff 友好,同步复杂度直接砍半。

这与仓库宪法中的本地优先、文件为真相原则并不冲突:SQLite 在此仅是待讨论的缓存层提案,不是已接受的持久化决定。graph 可考虑 entity / mention / edge 等派生表,但必须经 issue 与 ADR 评审。

数据存放理由
date · source · mood · entityMentions · tags · source_hash · 派发引用文件 YAML权威、该随内容走、人可编辑
倒排 / FTS 全文索引SQLite为查询而生,可从 vault 重建
entity↔memo 邻接 · 图的边SQLitegraph 视图查询,派生
embedding / 向量SQLite大、二进制、频繁 churn,别进文件;重算即可
已读态 · feed 排序物化 · on-this-day 预计算SQLite易变、设备本地、可丢

一句话划线: 权威的进文件,易变 / 派生 / 为性能的进 DB。写入永远单向——先写文件,再 re-index,绝不产生「只在 DB 里、又很重要」的状态。

04 · 显示与 Feed

D.刷的是编译产物,不是 raw

你自己 dump 的原始记录没必要回头再刷。值得刷的是被转化后的东西——feed 就是 transform-pipe 输出的渲染层,这也给 AI 编译找到了归宿。

  • 双区主页:上区「今天」写优先(捕获框 + 今日新 memo + 编译好落下的当日卡片);下区「流」是重现式刷面。热在上,冷/反思在下——对应暂存哲学的温度分层。
  • 排序不是「最新在前」,而是「此刻值得再看什么」。冷启动别上 ML:recency 衰减 + on-this-day + 未读 三个信号就够。
  • 别假装无限。让流有尽头。指标别盯 time-in-app,盯「关 App 时是否觉得重新连上了什么」——这是你自己的内容,奖赏是重新连接,不是新鲜刺激。
  • 分型卡片、统一设计语言(用你已有的 Space Grotesk / Inter);长按卡片看溯源——这张卡是哪几条 raw 喂出来的,能跳回暂存。AI 编译的东西,溯源就是信任。
  • Q3 与 Q4 在此接上:数据库存在的最大理由,就是让这个重现式 feed 跑得快、排得动。feed = 文件真相之上、DB 索引之上的一层视图。

05 · 必须保留的不变量

E.抽象不能破坏的三条

  • source_hash 去重内建进 skill 引擎:刻意排除 mood/entityMentions 的逻辑必须保留,否则一抽象就退回无限重编环。引擎要有「哪些输入参与 hash」的概念。
  • 离线优先的张力:capture 本地即时、可离线;compile 需 API,最终一致。捕获永不被 AI 阻塞。
  • FeatureFlags 复用:「哪些 transform / 卡片 skill 对哪个用户开」正好走已有的 FeatureFlags + FeatureFlagStore,Settings「实验功能」自动列出。

06 · 务实路径

F.别现在重写 v1.0

这是 v2 的形状。分阶段落地,每一步都可独立交付,且不打断上架。

Phase 0 · 现在不动主体 v1.0 上架优先

专注 App Store 提交(截图 / App Privacy / 登录 / ICP)。架构演进不阻塞发布。

Phase 1纯内部重构

把 CompilationService / WeeklyCompilation 内部收敛成声明式 recipe 抽象;把 vault 明确定义为稳定契约。对外行为不变,零风险。

Phase 2SQLite 派生索引 + 双区 Feed

引入可重建的 SQLite 索引(FTS5,后续 vector);主页改造成「今天 / 流」双区,流渲染编译卡片。

Phase 3daypage-vault MCP + PoC

做 MCP(list_raw · read_raw · write_compiled · list_entities),用一个 daily-compile skill 在 Claude Code / codex 里跑通同一个 vault——验证「手机只捕获、编译可插拔」。

Phase 4Out-pipes + 会话入口

daily-todo 生成器 + dispatch-ticktick / -reminders sink;微信(公众号 / 企业微信合规通道)作为会话捕获+命令入口。

Phase 5Skill registry + 开放扩展点

内置精选 skill 给普通用户;把 MCP + 文件作为开放扩展点,留给极客自己加 skill。同一底座同时接住小白与 Claude Code 玩家。

07 · 待定 / 需你拍板

G.开放问题

编译 runtime 落在端上还是服务端?

skill 的定义可优雅抽象,但执行 runtime 总得存在。单机用户的日编译在哪触发?端上瘦运行器(取代 BGTask)vs 服务端 cron——影响成本、离线性、隐私。

微信合规通道的具体限额?

个人号 hook 会封,须走公众号 / 企业微信;被动回复有超时、主动推送有窗口限制,慢编译只能异步回。需要我查一下当前最新的接口限额再定交互。

已读态要不要跨端?

目前建议 DB-only、设备本地、可丢。若你要「一端读过另一端也标记」,就得把已读态提升为需同步的状态——要么进文件,要么单独一条轻同步通道。取舍:一致性 vs 简单。
