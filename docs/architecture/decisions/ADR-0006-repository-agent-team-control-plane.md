# ADR-0006: Repository Agent Team control plane and canonical configuration

- **Status:** Accepted
- **Date:** 2026-08-07
- **Issue:** [#869](https://github.com/getyak/daypage/issues/869)

## Context

DayPage has grown from an iOS project into a multi-surface repository. The former root
guides contradicted each other and described obsolete targets, navigation, tests, and
design assets. Copied host skills drifted, an autogenerated Swift skill contained invalid
language conventions, and routine workflows could imply GitHub/release side effects.

The Go `agentry` runtime is a DayPage product component. Coupling repository development
coordination to that runtime would mix two security and lifecycle boundaries.

## Decision

1. Root `AGENTS.md` is the concise repository constitution.
2. `.agents/` is the canonical, host-neutral development control plane: manifest, roles,
   workflows, context routing, schemas, templates, and repository skills.
3. `CLAUDE.md`, `.claude/skills/`, `.codex/config.toml`, and `.codex/agents/` are thin
   host adapters. They may express host-required fields but cannot redefine architecture.
4. A lead creates a dependency-aware task graph; every worker gets explicit,
   non-overlapping owned and forbidden paths.
5. Task, handoff, and evidence payloads have machine-readable JSON schemas. Completion
   requires commands/results, conflict notes, and residual risk.
6. Context is layered and routed from indexes. Private data, secrets, unrelated history,
   and runtime logs are excluded by default.
7. Remote writes, destructive cleanup, deploys, tags, TestFlight, and releases are
   opt-in actions with explicit authorization. Release is a separate workflow.
8. `agentry/` remains a product runtime and does not become the development orchestrator.

## Consequences

- Agent hosts receive a consistent project contract without copied architecture essays.
- Parallel work has clearer ownership and independently reviewable handoffs.
- Repository validators can reject invalid skill metadata, incomplete host-agent fields,
  personal paths, tracked run artifacts, unpinned executable package commands, and unsafe
  default side effects. A small denylist catches known repeated stale project claims;
  broader architecture-fact drift still requires docs-steward and reviewer comparison
  against code/tests.
- Role and host adapter changes require keeping the manifest and contract tests current.
- Some legacy agent commands, copied skills, and historical documents remain outside this
  first migration and must be retired or adapted in follow-up work.

## Alternatives considered

- **Use `agentry` as the development control plane:** rejected because it couples repository
  governance to a product runtime and expands its trust boundary.
- **Keep independent Claude/Codex systems:** rejected because facts and safety policy drift.
- **Put every detail in root `AGENTS.md`:** rejected because large always-loaded context
  becomes stale; current details belong behind routed indexes.
